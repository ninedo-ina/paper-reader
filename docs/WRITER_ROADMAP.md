## 1. 需求原文要点

用户口述的四条核心意图（不是技术方案，是方向）：

1. **项目定位要从 reader 延伸到 writer。** 「它本身是一个 helper，但现在功能只聚焦在 reader 上。我想把这个功能往后延续一下，它还能做 writer。」
2. **创建出来的论文必须可以自由编辑。** 「它创建的这个地方，它创建的论文，它应该是可以自由编辑的……需要把编辑器做出来。」
3. **优先复用成熟开源成果。** 「你看一下现在有没有开源的最先进的论文编辑器，然后引入到我们这个项目里面，然后直接借用这开源项目去做我们论文编辑。」
4. **本轮只交付需求整理与迭代任务拆分。** 「你先把文档整理出来吧……把这个方向所有的需求整理完毕，整理完毕之后放在项目的文档里面。」同步远程的方式稍后另行告知。

**因此本轮的验收物就是本文档 + 选型文档，不是可运行的编辑器。** 编辑器本身的工作在本文第 5 节拆成迭代，从 `W1` 开始另行立项。

## 3. 关于"直接借用开源论文编辑器"：先纠正一个前提

调研（数据见 [PAPER_EDITOR_SELECTION.md](PAPER_EDITOR_SELECTION.md)，2026-09-26 取数）的结论很明确：

- **没有任何一款开源论文编辑器可以"直接引入"当本项目的手动论文编辑器。** 现存的学术编辑器要么是**完整应用**（Fidus Writer：自带 Django 后端 + 用户体系 + 自有数据库；Overleaf / TeXlyre：Node/TeX Live 后端 + 自有账号体系），要么是**排版引擎**（Typst、Pandoc、Quarto：没有编辑界面），要么是**桌面软件**（Zettlr）。
- 把完整应用塞进现有架构只有两条路：iframe 反代（引入第二套账号体系、第二套数据库、AGPL 网络条款风险，且无法与既有论文元数据/引用/分享打通），或抽源码（等于重写）。两者成本都高于自己搭编辑器层。
- **但"借用"在另外两层是完全成立的，而且应该借用**：
  - **编辑器层**借用 Tiptap 3（MIT，38.5k stars，与项目已有依赖同源），加上 MIT 的官方扩展（数学/表格/协作/唯一 ID/Markdown 等，均为 npm 实测可查的 MIT 包）；
  - **排版与导出层**借用 **Typst**（Apache-2.0，56.2k stars，Rust 单二进制）或 **Pandoc**（GPL-2.0，46.4k stars），以**独立进程**方式调用，把富文本导出成 PDF / DOCX / LaTeX；
  - **引用层**借用 CSL 生态（`@citation-js/plugin-csl` 等 MIT 包）+ 项目已有的 DOI/arXiv 元数据补全，而不是自己发明引文格式。

也就是说：**路线是对的，但"引入"的对象应该是"编辑器内核 + 排版引擎"，不是"某个论文编辑器产品"。** 详见选型文档第 2、4 节。

## 4. 需求归纳：writer 方向的九个主题

把用户口述的方向拆成可分工、可验收的主题。每个主题标注**依赖关系**与**是否可在本架构内独立交付**。

### W1 正文数据模型与持久化（地基，其余全部依赖它）

- **状态：已落地（`v0.1.52`，`REQ-202609-0257`，2026-09-26 UTC）** —— 按本节建议方案（`content_json` 权威 + `content_html` 派生 + `content_version`）实现，接口为 `GET|PUT /api/papers/{id}/content`，迁移 `V16__paper_content.sql`。
- **目标**：手动创建的论文有真正的正文，且刷新/换设备不丢。
- **交付物**：新增 `pr_papers` 正文存储（建议新增列而非新表，详见下）；`PUT /api/papers/{id}/content` 读写接口；正文与 `abstractText`（摘要）彻底分离。
- **关键设计选择（需要产品负责人拍板）**：存**编辑器 JSON**（可无损还原节点，前端 TipTap 用）还是存 **HTML/Markdown**（可读、可迁移、可被搜索引擎/导出直接消费）？建议**两者都存**：`content_json`（权威） + `content_html`（派生，便于导出与预览），派生字段可重建。
- **迁移**：新增 Flyway `V16`，`ALTER TABLE pr_papers ADD COLUMN content_json TEXT, ADD COLUMN content_html TEXT, ADD COLUMN content_version INTEGER`。**已应用的 V1-V15 不可修改**（[PROJECT_STATUS.md](PROJECT_STATUS.md) 第 9 节）。
- **依赖**：无。**必须最先做。**
- **验收标准**：新建手动论文 → 输入正文 → 保存 → 刷新页面正文仍在 → 重新登录仍在 → 后端直接查库可见内容；`PATCH /{id}`（元数据）不得再影响正文；删除论文仍清空正文（`PaperDeletionService` 需同步评估）。

### W2 编辑器内核与基础体验

- **状态**：✅ **已交付**（`v0.1.57`，`REQ-202609-0258`）——`FormatToolbar`（标题层级 H1/H2/H3+正文、粗/斜/下划线/删除线/行内代码、有序无序列表、引用、代码块、链接/移除链接、左中右对齐、撤销重做）+ **CJK 感知字符/词数统计**已上线；`onSave` 由 W1 接上、`content` 不再兜底 `abstractText`。**W2 原分配 `v0.1.55`，因并行 W3 先合入成为 `v0.1.56` 而放弃，顺延为 `v0.1.57` 并叠加在 W3 之上。** 未完：`dynamic({ssr:false})` barrel 仍未取舍；格式文案只补了 `zh`/`en`，其余 12 语言回退中文（留给 W9）。
- **目标**：把占位的 `PaperEditor` 做成能日常写东西的编辑器。
- **交付物**：工具栏（标题层级、粗斜体下划线删除线、列表、引用块、代码块、链接、对齐、撤销重做）或浮动菜单（BubbleMenu/FloatingMenu）；字符/词数统计；`onSave` 真正接上（先手动保存）；修掉 `PaperContentArea` 不传 `onSave` 的问题；启用已有的 `dynamic({ssr:false})` barrel 或明确删掉它（**不要两个都留**）；`content` 不再用 `abstractText` 兜底。
- **依赖**：W1（没有存储的工具栏没有意义，但工具栏本身可先做，只是无法验收）。
- **验收标准**：格式化操作后有可见变化且刷新后保留；`tsc --noEmit` / `vitest` / `next build` 全绿；新增组件测试锁定"工具栏存在 + 每一类格式能写进正文"。

### W3 自动保存与草稿保护

- **状态：已落地（`v0.1.56`，`REQ-202609-0259`，2026-09-26 UTC）** —— 四项交付物全部实现，三条验收标准在前端测试里以真实组件 + 假定时器钉住：`useAutosave`（2 秒防抖、失败 5 秒重试、`online` 立即重试）、编辑器头部状态指示（保存中 / 已保存 / 保存失败 + 重试）、`useUnsavedGuard`（`beforeunload` + 站内 `<a>` 捕获拦截）。**并发冲突是唯一需要后端配合的一条**：`PUT /api/papers/{id}/content` 新增可选 `baseVersion`，与库里 `contentVersion` 不符即 `409` / 业务码 `1008`（`ContentVersionConflictException`），前端把冲突当**状态**而非失败——**不自动重试**，提示「内容已被其他会话更新」并提供「加载最新」，绝不静默后写覆盖先写。**依赖顺序与原表不同**：本节列出的依赖是 W1 + W2，实际**在 W2 之前**落地——W3 于 `0.1.56` 先合入，W2 原分配的 `0.1.55` 因此作废，W2 顺延为 `v0.1.57` 并**加法叠加**在本轮的自动保存之上（`useAutosave` / `useUnsavedGuard` / `onReloadConflict` 一行未改）——自动保存本来就是挂在编辑器外层的通用防抖保存器，**不依赖工具栏**。两轮撞过的文件是 `common.json` 与 `PaperEditor.tsx`，已按文件逐条解决。**边界**：冲突只解决"谁的写入算数"，无历史版本、不能看差异也不能回滚（属 W6）；不传 `baseVersion` 的调用方仍会整篇覆盖（有意保留的向后兼容）。
- **目标**：写作不再依赖"记得点保存"。
- **交付物**：编辑停止 2 秒后防抖自动保存；保存中/已保存/保存失败（含重试）状态指示；离开页面前的未保存拦截（`beforeunload` + 路由切换确认）；并发/多标签编辑的冲突提示（后写覆盖需明确告知，不能静默）。
- **依赖**：W1、W2。（**实际上 W2 部分可放宽**：自动保存不需要工具栏，见上方状态行。）
- **验收标准**：断网停止编辑 → 恢复网络后内容自动落库；两个标签页先后编辑时，后保存者收到"内容已被更新"提示而不是静默覆盖；未保存时关闭标签页有浏览器原生确认。

### W4 学术写作能力（论文区别于普通文档的部分）

- **状态：已落地（`v0.1.54`，`REQ-202609-0260`，2026-09-26 UTC）** —— 五项交付物全部实现，且**验收标准里的三条都在测试里钉住了**：公式的编辑器和导出读的是同一份 KaTeX DOM（`getHTML()` 里必须有 `katex-html`/`katex-mathml`）；引用条目带可解析链接（`doi:` 前缀的 CSL item → `https://doi.org/…`）；**改文献顺序后正文引用编号自动重排**由 `academic-numbering.test.ts` 与 `academic-editor.test.tsx` 各测一遍。差异点：脚注**没有走 spike 也没有买 Tiptap Pro**，按本节"自研 Node"那条路线实现（正文引用节点持有脚注文本，文末列表的 `entries` 由编号插件推导回写）。
- **目标**：写出来的是论文，不是博客。
- **交付物**：
  - 数学公式：行内 + 独立公式块（`@tiptap/extension-mathematics`，MIT，基于 KaTeX，npm 实测 3.31.3）；
  - 表格：`@tiptap/extension-table`（MIT）；

## 6. 不能承诺的边界（诚实清单）

写在这里，避免后续被默认成"已经能做"：

1. **本轮没有写任何代码。** 现在打开手动创建的论文，仍然不能保存正文（见第 2 节证据）。
2. **"引入开源论文编辑器"不是一个可以直接勾掉的任务。** 见第 3 节，实际是"编辑器内核 + 排版引擎 + 引用生态"三件事。
3. **PDF 导出的排版保真度需要实测，不要提前承诺。** Typst/Pandoc 走的是"另写模板"路线，做不到"所见即所得地像素级还原网页"。公式、图表、参考文献是三个主要风险点。
4. **DOCX 导出只能做到"结构正确"，不保证与投稿系统模板完全一致。**
5. **协作编辑依赖安全债修复**，在 `/ws` 身份绑定修好之前不应上线。
6. **脚注能力在免费开源 Tiptap 生态中没有现成扩展**，需自研或采购，属于本规划中唯一"必然要额外投入"的功能点。
7. 本规划**没有覆盖后台管理端**（`/root/paperread-admin` 是独立仓库，见 [PROJECT_STATUS.md](PROJECT_STATUS.md) 第 1 节）。

## 7. 待产品负责人确认的问题

1. **正文存储形态**：只存编辑器 JSON，还是 JSON + HTML 双写？（建议双写，见 W1）
2. **版本号归属**：writer 是否作为中版本 `0.2.0` 立项目标，还是继续以 patch 滚动？
3. **手写内容的边界**：手动创建的论文是否允许"只有正文、没有摘要"？反过来，摘要是否要在编辑器中作为独立字段而非正文开头？
4. **脚注**：自研（成本可控但要维护）还是评估 Tiptap Pro 授权（省事但有持续付费与许可约束）？

7. **AI 写作辅助的边界**：是否接受"用户选区/正文会发送到第三方 Provider"这一事实，需要在 UI 上如何告知？
